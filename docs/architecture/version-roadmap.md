# 版本路线图

本文档是 `v0.2.1-wecom-reply-flow` 发布后的版本规划入口，用于统一当前收口、下一阶段功能和后续生产化边界。后续 agent 开发前应先阅读本文，再进入对应阶段计划。

## 当前发布点

| 版本 | 状态 | 说明 |
| --- | --- | --- |
| `v0.1-dify-ai-baseline` | 已完成 | Dify 双应用基线、API blocking 调用、基础 DSL 与系统契约。 |
| `v0.2-wecom-aibot-live` | 已发布 | 企业微信智能机器人长连接、@ 实时回复、历史消息补漏、非 @ 主动回复自动发送、实机链路可用。 |
| `v0.2.1-wecom-reply-flow` | 已发布 | @ 请求状态机、跨来源消息归并、占位 stream 生命周期保护、@ 与非 @ 回复稳定收口。 |

当前主线已经从“证明能接入 Dify 和企微”进入“可持续运营”的阶段。后续不恢复旧 Dify 四工作流边界，Dify 功能继续围绕真实业务链路重新定义。

## v0.2.1 P0 消息系统架构修复

**目标：** 在不引入大功能的前提下，修复当前消息系统的必需架构缺口，让实时 @、补漏恢复和主动回复具备稳定的请求归属、执行状态和重复抑制。

**范围：**

- 按 [P0 消息系统架构修复计划](./p0-message-system-architecture-repair.md) 完成 @ 请求认领、跨来源消息归并、AI 执行状态判断、占位 stream 生命周期保护。
- 确认 @ 回复、非 @ 主动回复、重复消息抑制、机器人消息排除、非法 Dify 输出不发送。
- `messages.userid` 作为必填契约处理；如果企微消息缺失 `userid`，只记录错误日志，便于后续排查，不做身份猜测和兜底归属。
- 主动回复发送可靠性与实机回归清单合并，由实机测试一次覆盖。
- 保留当前 Dify API blocking 模式；不引入 streaming。

**验收：**

- 创建者和非创建者账号均可触发对应机器人能力。
- 快速连续 @ 同一机器人时，每条业务请求最多进入一次 Dify，最多发送一次最终回复，且回复内容与问题一一对应。
- 补漏 worker 不会抢占正在运行的实时 @，只恢复真正遗漏、失败或超时的 @。
- 非 @ 消息经补漏拉取后能入库、跑主动提醒判断，并在满足条件时自动发送。
- 日志中能定位缺失 `userid`、Dify 非法输出、企微发送失败等问题。

**暂不做：**

- 新前端。
- Redis 缓存。
- 持久化任务队列。
- 分布式锁。
- 复杂限流和权限系统。

## v0.3 AI 记忆与运营界面

**目标：** 从“机器人能稳定回复”升级为“系统能沉淀会话、更新画像、让人查看和运营”。

### 必做模块

1. **会话沉淀 / 会话摘要**

   第一版先做每日会话切分：输入单日全量群消息和用户信息，包含机器人回复；Dify 只输出切分位置数组，自建系统校验后生成会话段并入库。后续再补摘要增强。

2. **用户画像自动更新**

   基于一个会话的全部消息、一个目标 `userid` 和该用户原画像生成更新画像。一个会话内多用户画像更新由系统创建多个异步请求；不同用户可并行，同一用户必须串行或做版本冲突保护。

3. **第一版前端界面**

   先做运营和排障型界面，不做复杂数据大屏。首版应能查看消息、AI 运行记录、outbox 发送状态、会话摘要、用户画像和错误日志线索。

4. **Dify 工作流补齐**

   新增面向会话切分和画像更新的 Dify 应用或工作流。继续使用 `inputs.payload` + `response_mode=blocking`，输出必须是正式 JSON 字段，不在 JSON 外输出自然语言。Dify 内部输出不规范时修复两次，自建系统最多重试一次。

5. **回复工作流画像化**

   画像可用后，重写 `group_knowledge_reply` 和 `chat_proactive_reminder` 的输入上下文，由系统传入用户画像进行个性化输出。两个工作流输出结构保持不变，避免破坏已稳定的发送链路。

### Dify 边界

- Dify 可以做：摘要、意图理解、回复生成、画像建议、证据归纳、结构化输出。
- Dify 不做：企微发送、数据库写入、幂等、重试、调度、权限、最终业务状态机。
- Dify 不允许编造：`msgid`、`userid`、数据库中不存在的事实来源。
- 非 @ 主动回复继续 blocking；streaming 只保留给后续 @ 实时回复体验升级。

### 前端边界

首版前端优先服务开发和运营，不追求完整管理后台。建议页面：

- 消息列表：按群、用户、时间、@/非 @、机器人/用户筛选。
- AI 运行记录：查看 Dify 输入摘要、输出、状态、错误原因和耗时。
- Outbox：查看待发送、已发送、失败、跳过原因。
- 会话摘要：查看会话片段、摘要、证据消息、版本。
- 用户画像：查看当前画像、历史版本、证据来源、待审核更新。
- 实机测试面板：显示当前长连接状态、补漏 worker 状态和最近错误。

### 验收

- 能从数据库中的真实消息生成会话摘要，并能追溯到原始 `msgid`。
- 能基于真实 `userid` 生成画像更新建议，并拒绝缺失 `userid` 的更新。
- 前端可以看到一条消息从入库、AI 运行、outbox 到发送结果的链路。
- 出错时可以从界面或日志定位是 Dify、企微发送、入库还是数据契约问题。

## v0.4 可观测性与运营强化

**目标：** 在第一版前端可用后，把排障能力从日志和数据库查询升级为可交互的运营工具。

建议范围：

- AI 运行详情页：输入、输出、校验失败原因、兜底结果、耗时。
- 发送可靠性页：发送失败重试、跳过原因、重复抑制命中记录。
- 会话和画像审核流：人工确认、驳回、回滚、版本对比。
- 基础权限：区分开发排障、运营查看和管理员操作。

## v0.5 生产化与性能优化

**目标：** 当真实使用规模或前端访问暴露瓶颈后，再引入缓存、队列和分布式能力。

建议范围：

- Redis 缓存：用于高频查询、前端列表缓存、短期已处理集合。
- 持久化任务队列：替代进程内后台任务，提高失败恢复能力。
- 分布式锁：用于多实例部署时的补漏任务、主动回复去重和 outbox 消费。
- 更细限流：按群、按用户、按 Dify 应用、按企微发送通道限制。
- 数据库升级评估：当 SQLite 无法支撑并发写入和前端查询时迁移 PostgreSQL。

## 暂缓清单

- Dify streaming：只用于 @ 实时回复体验升级，非 @ 主动回复不需要流式。
- 大屏式统计报表：等前端基础能力和数据口径稳定后再做。
- 复杂客服工单系统：当前先保持消息、会话、画像、发送链路闭环。
- 按机器人/用户拆分消息表：当前继续单表，使用 `sender_type` 和索引过滤。
- Webhook 异步回收：当前主链路继续 Dify API blocking。

## 开始 V0.3 前检查

- 当前 `main` 应基于 `v0.2.1-wecom-reply-flow` 发布点继续推进。
- 建议新建开发分支：`codex/v0.3-ai-memory-admin-ui`。
- 先补 V0.3 详细实施计划，再写代码。
- 先设计数据读写和 Dify 输出契约，再设计前端页面。
- 每个阶段都保留可实机测试路径，避免只完成离线功能。

## V0.3 推荐启动顺序

详细编排见 [V0.3 AI 记忆工作流编排计划](./v0.3-ai-memory-workflow-plan.md)。

1. **契约冻结，串行先做**

   盘点 `messages`、`conversation_segments`、`user_profiles`、`user_profile_facts`、`ai_runs` 的当前字段和读写路径，确定会话切分、画像更新和回复画像化需要的输入 payload、输出 JSON 和落库字段。

2. **会话切分，先形成闭环**

   先做每日单群消息切分：读取单日全量消息、调用 Dify 输出切分点、校验切分点、写入 conversation_segments。这个模块是画像更新和前端展示的上游。

3. **画像更新，依赖会话切分输出**

   在会话切分稳定后，为每个会话参与用户创建画像更新请求：读取该会话全部消息、目标用户原画像，调用 Dify 生成更新画像，由自建系统校验 `userid`、证据、版本后写库。画像更新请求必须有状态机，不同用户可并行，同一用户不能并发覆盖。

4. **回复工作流画像化**

   画像可用后，重写 @ 回复和非 @ 主动回复的 Dify payload，把用户画像传入 Dify 做个性化输出。输出字段保持当前结构，避免影响发送链路。

5. **前端基础，可与画像后端部分并行**

   当前端所需 API 字段确定后，可以并行做页面骨架、消息列表、AI 运行记录、outbox 状态、会话摘要和用户画像详情。前端第一版先服务排障和运营，不做复杂权限和统计大屏。

6. **实机回归，串行收口**

   每完成一个 AI 写库模块，都要用真实消息或数据库回放验证：Dify 输出合法、证据可追溯、缺失 `userid` 会拒绝画像更新、画像版本不会并发覆盖、前端能查到同一条链路。

### 可并行安排

- 会话切分 Dify DSL 与后端校验 schema 可以并行，但必须共享同一份 `split_positions` 输出契约。
- 画像更新 Dify DSL 与 `profile_update_requests` 状态机可以并行，但画像写库规则必须以后端契约为准。
- 回复工作流画像化必须等画像读取接口稳定后再做。
- 前端消息列表、AI 运行记录、outbox 状态页可以并行，因为它们主要读取已有表。
- Redis、持久队列、分布式锁和 streaming 不进入 V0.3 并行开发池。
