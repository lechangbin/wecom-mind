消息接收后的执行链路

这张图基于当前长连接与补漏更新分支。结论很直接：智能机器人长连接 Worker 已经能把实时 @ 消息串到入库、Dify、outbox 和 callback-bound stream 发送；非 @ 消息由历史补漏 Worker 短窗口拉取、入库、数据库窗口扫描和 Dify 主动提醒，自动发送则由长连接 Worker 复用同一条回复机器人连接完成。

当前自动执行 保留手动调试入口 可并行执行 当前断点或风险 建议新增调度 Module

4. 哪些顺序，哪些可并行

必须顺序

长连接 frame

必须先收到真实 frame，才能保留原始 msgid/chatid/userid。

消息归一化

必须先有 Message，才能做 @ 判断和窗口扫描。

Dify 输出校验

必须先校验输出，再创建 outbox。

发送状态回写

必须根据企微返回更新 sent/failed。

可以并行

不同群消息

不同群的 frame 可并行处理；同一 msgid 由入库幂等保护。

@ 分支与窗口分支

同一条消息入库后，@ 答疑和窗口主动答疑可以由不同 Worker 分别决策。

不同 Dify app

group_knowledge_reply 与 chat_proactive_reminder 使用不同 key，可独立限流和执行。

不同 outbox

独立 outbox 可并行发送，但同一幂等键只能发送一次。

5. 建议的自动闭环

自动

AiBot 长连接 Worker

常驻进程接收消息 frame，不需要公网 callback。

自动

Frame Normalizer

直接生成 MessageIngestRequest，复用入库模块。

新增

Incoming Message Orchestrator

process_incoming_aibot_frame 决定是否触发 @ 答疑。

并行

AI 分支任务

@ 答疑、主动答疑分别执行，输出只写 ai_runs 和 outbox。

后续

Outbox Worker

当前 aibot_ws 自动发送由长连接 worker 消费新建 pending proactive outbox；后续可独立消费 pending outbox，统一限流、重试、失败记录。

自动

企微发送

reply/proactive 场景优先走智能机器人长连接 send_message，状态回写。

6. 架构改进候选

P0 实机闭环

完善主动提醒调度

当前常驻补漏 worker 已接入，下一步重点是自动发送复测、发送失败重试和主动答复频控。

P0 实机闭环

接真实历史消息源

把 get_msg_chat_list / get_message 适配到 message_reconcile，使用短窗口补漏，不作为主接收入口。

P1 稳定性

补 InteractionRun 状态

现在有 ai_runs/outbox，但缺少一次消息交互的总状态。新增状态可让排障知道卡在 normalize、Dify、outbox 还是 send。
