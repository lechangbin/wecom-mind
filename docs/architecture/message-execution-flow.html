1. 为什么现在未自动化

回调只确认接收

POST /api/wecom/callbacks/mcp 完成验签、记录 callback，并创建 MessageIngestionJob。在 real 模式下它必须尽快返回 success 给企微，不能在这个请求里长时间跑 Dify 和发送。

后续步骤都是独立 Interface

归一化、触发评估、主动答疑、outbox 发送分别暴露为不同路由。代码里没有一个“收到消息后继续推进下一步”的 Orchestrator Module。

缺少后台 Worker

系统有 pending job 和 pending outbox 的数据模型，但没有常驻 Worker 或调度器自动消费它们。没有消费者，队列表就只是状态记录。

4. 哪些顺序，哪些可并行

必须顺序

回调落库

必须先有 callback/job，才能可靠重放。

消息归一化

必须先有 Message，才能做 @ 判断和窗口扫描。

Dify 输出校验

必须先校验输出，再创建 outbox。

发送状态回写

必须根据企微返回更新 sent/failed。

可以并行

不同 callback job

不同群、不同 callback 的 normalize job 可并行，但同一 job 内当前按消息顺序处理。

@ 分支与窗口分支

同一条消息入库后，@ 答疑和窗口主动答疑可以由不同 Worker 分别决策。

不同 Dify app

group_knowledge_reply 与 chat_proactive_reminder 使用不同 key，可独立限流和执行。

不同 outbox

独立 outbox 可并行发送，但同一幂等键只能发送一次。

6. 架构改进候选

P0 实机闭环

新增 Interaction Orchestrator Module

把“消息入库后应该触发哪些 Dify 分支”集中到一个 Interface 后面。收益是 Locality：触发规则、顺序、并行、幂等都在一处维护。

P0 实机闭环

新增两个 Worker Adapter

一个消费 MessageIngestionJob，一个消费 OutboxMessage。收益是 Leverage：现有手动接口仍可保留，但自动化不依赖人工点击。

P1 稳定性

补 InteractionRun 状态

现在有 ai_runs/outbox，但缺少一次消息交互的总状态。新增状态可让排障知道卡在 normalize、Dify、outbox 还是 send。
