# 需求与模块设计

## 1. 项目定位

本项目是一个课程项目性质的企业微信智能机器人系统。系统基于企业微信能力获取群聊消息，使用自建系统完成消息资产沉淀、业务编排和数据治理，使用 Dify 完成 AI 工作流。

项目重点是功能闭环和架构清晰：

- 能接入企微群聊数据。
- 能响应用户 @ 消息。
- 能进行定时意图识别并主动提醒用户。
- 能完成智能会话切分。
- 能完成用户画像分析。
- 能为后续前端后台提供统计和查询数据。

## 2. 功能分类

### 2.1 基础接入能力

| 功能 | 必要性 | 说明 |
| --- | --- | --- |
| 企微 MCP/webhook 回调接收 | 必须 | 接收群消息通知或消息数据 |
| 群消息拉取 | 必须 | 根据回调事件、游标或时间范围拉取消息 |
| 消息原始数据保存 | 必须 | 保存企微原始 payload，便于排查和回放 |
| 消息标准化 | 必须 | 将不同类型消息转成统一内部结构 |
| 幂等排重 | 必须 | 防止企微重试或 Worker 重跑造成重复消息 |
| 附件元数据处理 | 可选 | 图片、文件、语音等先保存元数据，内容下载可后置 |

### 2.2 机器人交互能力

| 功能 | 必要性 | 说明 |
| --- | --- | --- |
| @ 消息识别 | 必须 | 用户 @ 机器人时触发即时回复 |
| 引用消息上下文保存 | 必须 | 保存用户引用内容，支撑上下文理解 |
| 流式回复 | 重要 | 若企微能力支持，则用于 @ 实时回复 |
| 普通回复 | 必须 | 流式不可用时的兜底 |
| 主动 @ 用户 | 必须 | 定时意图识别命中后提醒对应用户 |
| 关键词定时触发 | 重要 | 系统定时扫描已入库消息窗口，命中关键词后作为意图识别输入线索 |
| 模板卡片 | 可选 | 后续用于交互按钮、确认、反馈 |

### 2.3 AI 工作流能力

| 功能 | 必要性 | 说明 |
| --- | --- | --- |
| Dify 工作流注册 | 必须 | 管理工作流用途、版本和 schema |
| Dify 调用日志 | 必须 | 保存输入、输出、耗时、状态和错误 |
| 通用回复生成工作流 | 必须 | 根据 @ 消息或意图识别结果生成最终回复 |
| 意图识别与动作决策工作流 | 必须 | 基于定时扫描窗口和关键词线索识别提醒、待办、跟进等意图 |
| 会话切分工作流 | 必须 | 根据时间窗口和 LLM 判断生成会话边界 |
| 用户画像工作流 | 必须 | 基于历史画像生成或更新用户画像 |
| 输出 JSON 校验 | 必须 | 防止 Dify 输出不符合系统要求 |

### 2.4 数据治理能力

| 功能 | 必要性 | 说明 |
| --- | --- | --- |
| 群聊档案 | 必须 | 保存 chatid、群名称、状态 |
| 用户档案 | 必须 | 保存 userid、昵称、部门等基础信息 |
| 消息查询 | 必须 | 支撑 AI 上下文和前端查询 |
| 会话摘要 | 必须 | 保存切分后的会话摘要 |
| 用户画像 | 必须 | 保存用户画像快照和画像事实 |
| 审计日志 | 重要 | 记录关键写入、发送、AI 调用 |

### 2.5 运维与统计能力

| 功能 | 必要性 | 说明 |
| --- | --- | --- |
| 任务队列 | 必须 | 支撑消息拉取、AI 分析、发送重试 |
| 失败重试 | 必须 | 外部 API 调用失败后可恢复 |
| 调用限流 | 重要 | 保护企微和 Dify 接口 |
| 状态监控 | 重要 | 统计任务堆积、失败、耗时 |
| 前端统计接口 | 重要 | 为课程展示预留数据 |

## 3. 核心模块需求

### 3.1 WeCom Callback Gateway

职责：

- 提供公网 HTTPS 回调地址。
- 接收企微 MCP/webhook 回调。
- 校验签名、时间戳、nonce、来源 IP。
- 保存回调原始数据。
- 快速返回成功。
- 将耗时处理转交后台任务。

输入：

- 企微回调 query 参数。
- 企微回调 body。

输出：

- 回调记录。
- 消息拉取任务或消息入库任务。

关键要求：

- 回调接口不能等待 Dify。
- 回调必须可幂等处理。
- 回调异常必须记录原始请求摘要。

### 3.2 WeCom Message Puller

职责：

- 根据回调事件或游标拉取群消息。
- 管理每个群或机器人维度的拉取游标。
- 支持失败重试和补偿拉取。
- 将拉取到的消息写入消息处理流水线。

关键要求：

- 同一 chatid 同一时间只能有一个有效拉取游标推进任务。
- 拉取结果必须根据企微 msgid 或内部哈希排重。
- 拉取失败不能丢失游标。

### 3.3 Message Ingestion Service

职责：

- 保存原始消息。
- 转换标准化消息。
- 建立消息与群、用户、引用内容、附件之间的关系。
- 触发后续规则评估。

关键要求：

- 原始消息和标准化消息都要保留。
- 标准化失败的消息也要进入异常表或异常状态。
- 消息入库要有幂等键。

### 3.4 Trigger Router

职责：

- 判断消息或消息窗口是否命中触发规则。
- 支持 @ 事件触发、关键词定时扫描、定时意图扫描、手动触发。
- 决定调用哪个 Dify 工作流。
- 创建 AI 调用任务。

关键要求：

- @ 触发来源于企微 @ 事件回调或长连接实时消息，由自建系统判断后调用 `reply_generation`。
- 关键词定时扫描触发来源于系统调度器扫描已入库消息窗口，不依赖企微实时关键词事件。
- 关键词命中只作为 `intent_detection` 输入线索，不单独对应 Dify 回复工作流。
- 触发规则和 Dify 工作流不要写死在代码里。
- 每次触发要保存触发原因。
- 同一消息对同一规则要避免重复触发。

### 3.5 Dify Gateway

职责：

- 统一调用 Dify。
- 管理 Dify workflow code、version、API endpoint、密钥。
- 组装输入 JSON。
- 接收 blocking 或 streaming 输出。
- 保存 Dify 调用记录。
- 对 Dify 输出做 JSON schema 校验。

关键要求：

- Dify 的错误不能直接影响消息入库。
- Dify 输出必须经过自建系统校验后才能写入核心业务表。
- 流式输出后续只用于 `reply_generation` 的 @ 实时回复场景。

### 3.6 Conversation Intelligence Service

职责：

- 管理会话切分任务。
- 构造消息窗口。
- 调用 Dify 会话切分工作流。
- 保存会话编号、起止消息、摘要、关键词和参与人。

关键要求：

- 会话编号由自建系统生成或确认。
- Dify 不能直接决定不存在的消息边界。
- 会话切分结果支持重新分析和版本更新。

### 3.7 User Profile Service

职责：

- 管理用户画像分析任务。
- 汇总用户个人消息和参与会话。
- 调用 Dify 用户画像生成与更新工作流。
- 保存画像事实、证据消息、置信度和画像快照。

关键要求：

- 每条画像事实必须有来源或证据。
- 低置信度结果可以保存但不能进入主画像快照。
- 画像更新要保留历史版本。

### 3.8 Outbound Dispatcher

职责：

- 统一发送企微消息。
- 支持普通回复、流式回复、主动消息、@ 指定用户、模板卡片。
- 管理发送状态和失败重试。
- 控制发送频率。

关键要求：

- 所有发送动作先写入 outbox，再执行发送。
- 发送成功后保存企微返回的 msgid 或回执。
- 发送失败必须记录错误码、错误信息和重试次数。

### 3.9 Admin & Analytics API

职责：

- 为未来前端提供查询和统计接口。
- 支持消息查询、会话摘要查询、用户画像查询、Dify 调用日志查询。
- 支持基础看板统计。

关键要求：

- 前端暂时不是重点，只预留必要接口。
- 统计数据优先从业务表聚合生成，必要时后续增加统计宽表。

## 4. MVP 范围

MVP 必须完成：

- 企微回调接收。
- 群消息入库。
- @ 消息识别。
- 调用 Dify 通用回复生成工作流生成回复。
- 发送普通回复或流式回复。
- 意图识别与动作决策。
- 主动发送 @ 消息。
- 会话切分。
- 用户画像分析。
- Dify 调用日志。
- 基础查询接口。

MVP 可以延后：

- 完整前端统计看板。
- 模板卡片交互。
- 附件内容全文解析。
- 多租户配置。
- Internal MCP Server。
- 复杂权限系统。
