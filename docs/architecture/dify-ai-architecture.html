Dify AI 功能重建架构

新版路线以交互闭环优先：首批只建设两个 Dify 应用，分别负责 @ 触发的群主题知识答疑和意图触发的知识答疑主动回复。自建系统继续承担状态、校验、引用、@、发送、幂等和审计。

首批：双应用 调用：blocking 知识库：Dify 内检索 画像：自建系统传入 流式：后续计划

1. 三方边界总览

谁产生消息、谁做 AI、谁执行业务动作，一眼分清。

企业微信 消息通道
消息入口 群消息、@ 事件、用户发言进入自建系统。
消息出口 接收自建系统发送的正文、@ 用户和引用回复。
自建系统 状态中心
上下文组装 读取消息、画像、已处理记录，构造 Dify 入参。
业务执行 校验输出、引用原消息、@ 用户、写 outbox、幂等和审计。
Dify AI 判断与生成
知识答疑 检索群主题知识库，判断范围并生成 Markdown 答案。
主动回复 从聊天窗口中识别知识答疑意图，检索知识库并生成主动回复字段。

2. 首批交互闭环主链路

首批不做 streaming，先让 blocking 链路可审计、可发送、可回放。

企微消息进入

用户在群内 @ 机器人，或聊天窗口中出现可被意图识别触发的知识答疑需求。

→

自建系统组装上下文

根据场景传入触发消息、近期消息、轻量画像、已回复和已提醒记录。

→

Dify 完成 AI 判断

@ 答疑或意图主动回复应用返回结构化结果；自建系统校验后再执行发送。

3. 首批两个 Dify 应用

应用按业务场景拆分，避免一个 Prompt 同时承担答疑和提醒。

group_knowledge_reply

群主题内部知识答疑

Dify 侧 Knowledge Retrieval Markdown
Start 接收问题、触发消息、用户、群聊上下文和轻量画像。
知识库检索群主题资料，补充长期知识。
范围判断：不属于群主题答疑时输出 out_of_scope。
范围内才生成 Markdown 正文。
范围内输出：action、content。
越界输出：action=out_of_scope、reason，不输出可发送回答正文。

chat_proactive_reminder

意图触发的知识答疑主动回复

Dify 侧 Knowledge Retrieval blocking 猜你想知道
Start 接收触发消息、群聊窗口、成员、消息列表和已处理记录。
知识库检索意图相关资料，补充长期知识。
判断是否适合主动补充答案；低置信度、已处理或依据不足时不发送。
生成“猜你想知道这个问题答案”的 Markdown 回复和执行字段。
自建系统校验后完成 @、引用原消息和 outbox 入队。
最小执行输出：should_send、target_userids、quote_msgid、content、confidence。
历史 Dify 应用、旧 DSL 和旧节点配置只作为迁移对象，不作为新版应用边界。新版主图只认上面两个首批应用。

4. 数据与上下文来源

Dify 不直接承担首批实时链路的数据访问责任。

群聊消息

自建系统从消息表读取触发消息、近期消息和意图识别窗口，传给 Dify。

用户画像

自建系统读取轻量画像和事实摘要，作为答疑语气和背景上下文。

群主题知识库

Dify 使用内置知识库检索节点，维护内部知识答疑资料。

已处理记录

自建系统传入已回复、已主动触发、待发送和已发送记录，主动回复据此降重。

5. 执行责任边界

AI 可以判断和生成，但最终业务动作必须回到自建系统。

Dify 负责

范围判断、知识库检索、@ 答疑正文、意图触发主动回复正文和置信度。

系统校验

校验 JSON、目标用户、引用消息、置信度、重复提醒和业务状态。

发送动作

系统完成 @ 原用户、引用原消息、创建 outbox、发送和失败重试。

越界提示

Dify 只输出越界状态；系统发送配置化固定提示，不由 Dify 生成。

实时 @ 答疑中，回复风格要明确回答触发问题；意图主动回复中，回复风格更像“猜你想知道这个问题的答案”。目标用户和 quote_msgid 最终必须被自建系统校验。

6. 后续阶段

首批先闭环交互，后台智能和流式能力后置。

流式回复

后续只考虑实时 @ 答疑流式化；意图主动回复继续 blocking。

画像自动更新

后台型应用可通过固定 SQL 或只读插件查询数据库，再产出画像更新建议。

会话沉淀

将聊天窗口整理成主题摘要、关键事项和可被画像/答疑复用的上下文。

只读查库治理

为后台 Dify 应用设计数据库只读账号、视图、固定查询和版本管理。
