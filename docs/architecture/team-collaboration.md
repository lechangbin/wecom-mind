# 团队协作与分工边界

## 1. 协作背景

本项目主体系统由 agent 辅助开发，Dify 工作流由团队成员分工实现。为了避免自建系统和 Dify 工作流互相阻塞，双方必须以稳定 JSON 契约协作。

核心原则：

- 自建系统负责主流程、数据状态和对外接口。
- Dify 团队负责 AI 工作流配置、Prompt、模型选择和输出质量。
- 双方不直接修改对方内部实现。
- 所有联调都围绕输入 JSON、输出 JSON、错误样例和验收标准进行。

## 2. 分工总览

| 领域 | 负责人 | 主要交付物 |
| --- | --- | --- |
| 企微 MCP/webhook 接入 | 主体系统 | 回调接口、签名校验、消息拉取任务 |
| 消息入库与标准化 | 主体系统 | 原始消息表、标准消息表、排重逻辑 |
| 触发规则 | 主体系统 | @ 事件触发、关键词定时扫描线索、定时任务触发 |
| Dify Gateway | 主体系统 | Dify 调用封装、日志、schema 校验 |
| Dify 工作流 | Dify 团队 | 工作流配置、Prompt、输出 JSON |
| 会话切分写库 | 主体系统 | 会话编号、摘要、版本、状态 |
| 用户画像写库 | 主体系统 | 画像事实、证据、快照、版本 |
| 企微消息发送 | 主体系统 | 普通回复、流式回复、主动 @ 消息 |
| 前端统计接口 | 主体系统 | 查询接口、统计接口 |

## 3. 主体系统职责

主体系统必须完成：

- 接收企业微信回调。
- 拉取或接收群消息。
- 保存原始消息和标准化消息。
- 判断消息触发类型：@ 来自企微事件或长连接实时消息，关键词来自系统定时扫描。
- 将关键词命中结果作为 `intent_detection` 的输入线索，而不是单独交给 Dify 生成回复。
- 为 Dify 构造输入 JSON。
- 调用 Dify 工作流。
- 校验 Dify 输出 JSON。
- 保存 AI 调用日志。
- 将合法结果写入业务表。
- 发送企微消息。
- 提供后续前端查询和统计接口。

主体系统不负责：

- 具体 Prompt 优化。
- Dify 节点编排细节。
- 模型参数调优。
- Dify 工作流内部知识库配置。

## 4. Dify 团队职责

Dify 团队必须完成：

- 根据约定输入 JSON 配置工作流变量。
- 所有工作流 Start 节点只声明 `payload: json_object`。
- 编排 LLM、条件判断、HTTP 请求、代码节点等 Dify 节点。
- 输出符合约定 schema 的 JSON。
- 为每个工作流提供测试样例。
- 记录工作流版本和变更说明。
- 与主体系统联调失败样例。
- 确保 `intent_detection` 只输出动作建议，不输出最终回复正文。
- 确保 `reply_generation` 是唯一输出可发送消息正文的 Dify 工作流。

Dify 团队不负责：

- 直接写业务数据库。
- 直接发送企微消息。
- 维护企微回调接口。
- 处理消息游标、排重和重试。
- 修改自建系统数据库结构。

## 5. 协作接口

双方只通过以下契约协作：

1. 工作流编码：`workflow_code`
2. 工作流版本：`workflow_version`
3. 输入 JSON schema
4. 输出 JSON schema
5. 成功样例
6. 失败样例
7. 置信度规则
8. 联调验收标准

任何 Dify 工作流变更，如果不改变输出 schema，可以由 Dify 团队独立调整。

如果变更输出字段、字段类型或业务含义，必须同步主体系统更新 schema 校验和结果处理逻辑。

## 6. 工作流交付清单

每个 Dify 工作流交付时必须提供：

- 工作流名称。
- `workflow_code`。
- Dify 应用 ID 或工作流 ID。
- 工作流版本。
- 输入变量说明。
- 输出 JSON 示例。
- 至少 3 条成功测试样例。
- 至少 2 条边界测试样例。
- 失败时的兜底输出。
- 推荐模型和参数。
- Prompt 版本说明。

## 7. 联调流程

推荐联调流程：

1. 主体系统提供业务 payload JSON。
2. Dify 团队在 Dify 中完成工作流配置。
3. Dify 团队用 API blocking 方式验证 `inputs.payload` 和输出 JSON。
4. 主体系统接入真实 Dify API endpoint。
5. 主体系统保存 `ai_runs` 调用日志。
6. 主体系统校验 Dify 输出。
7. 双方根据失败样例修正契约或工作流。
8. 验收通过后固定 `workflow_version`。

## 8. 验收标准

一个 Dify 工作流可接入主体系统的最低标准：

- Start 节点能通过 `payload` 完整接收主体系统 JSON。
- 输出 JSON 可被解析。
- 输出字段符合 schema。
- 主体系统校验通过率达到约定标准。
- 低置信度场景能返回可识别结果。
- 异常场景不会输出自然语言散文替代 JSON。

推荐通过标准：

- 普通样例通过率不低于 90%。
- 边界样例通过率不低于 70%。
- JSON 格式错误率为 0。

## 9. 变更管理

Dify 工作流变更分三类：

| 类型 | 示例 | 是否需要主体系统改动 |
| --- | --- | --- |
| Prompt 变更 | 优化摘要语言、调整判断标准 | 否 |
| 参数变更 | 更换模型、温度、最大 token | 否 |
| 契约变更 | 新增字段、删除字段、改变字段类型 | 是 |

契约变更必须更新：

- `api-contracts.md`
- `docs/dify-development/`
- `ai_workflows.output_schema`
- 主体系统输出校验逻辑

## 10. 风险控制

主要风险：

- Dify 输出非 JSON。
- Dify 输出字段缺失。
- Dify 返回不存在的 msgid 或 userid。
- Dify 置信度虚高。
- Dify 工作流版本变更后主体系统未同步。

控制方式：

- 主体系统统一做 schema 校验。
- 主体系统校验 msgid、userid、chatid。
- 低置信度结果不自动写入主画像或自动发送。
- Dify 工作流上线前固定版本。
- 所有调用保存 `ai_runs` 日志。
