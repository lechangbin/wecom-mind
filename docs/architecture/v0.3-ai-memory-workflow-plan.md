# V0.3 AI 记忆工作流编排计划

本文档用于编排 V0.3 的会话切分、用户画像更新、回复工作流画像化改造。当前阶段不重写项目，不引入 Redis、分布式锁或 Dify streaming。

## 1. 总体目标

V0.3 需要完成三条能力链：

```text
每日消息 -> 会话切分 -> 会话入库
会话入库 -> 多用户画像更新请求 -> 画像版本入库
画像可用 -> @ 回复 / 非 @ 主动回复传入画像 -> 个性化输出
```

Dify 负责结构化判断和生成；自建系统负责状态机、并发控制、校验、重试、写库、日志。

## 2. 阶段一：会话切分工作流

### 2.1 目标

每天一次读取单日全量群消息，包含用户消息和机器人回复，由 Dify 输出切分位置数组，自建系统按切分点生成 `conversation_segments`。

当前全量测试入口：

- 手动触发：`POST /api/ai-memory/full-test/run`
- 常驻定时 worker：`scripts/run_ai_memory_full_test_worker.py`
- 一键启动脚本会在 `AI_MEMORY_FULL_TEST_ENABLED=true` 时自动启动该 worker。
- 本地 `.env` 已增加 `DIFY_CONVERSATION_BOUNDARY_DETECTION_API_KEY` 与 `DIFY_USER_PROFILE_UPDATE_API_KEY`，用于真实 Dify blocking 调用。
- 默认 `AI_MEMORY_FULL_TEST_ENABLED=false`，避免服务启动后立即对历史消息库大量调用 Dify；实测时再显式打开。

手动触发示例：

```json
{
  "target_date": "2026-06-04",
  "chatids": ["CHAT_A"],
  "run_profiles": true
}
```

返回重点：

- `chat_results[]`：每个群的会话切分运行结果。
- `profile_results[]`：每个会话内每个用户的画像更新运行结果。
- `segment_count`：本轮生成或复用的会话段数量。
- `profile_update_count`：本轮实际 create/update 的用户画像数量。

幂等保护：

- 同一天同一群如果已经存在 active `conversation_segments`，全量测试入口会复用既有会话段，不再次调用 `conversation_boundary_detection`。
- 同一 `conversation_no + userid` 如果已经有画像事实证据落库，画像更新会标记为 `already_updated` 并跳过。
- 这只是 V0.3 全量测试保护；正式生产状态仍以后续 `profile_update_requests` 状态机为准。

### 2.2 Dify 工作流

工作流建议命名：

```text
conversation_boundary_detection
```

输入：

```json
{
  "payload": {
    "chat": {},
    "window": {},
    "messages": [],
    "users": [],
    "existing_segments": [],
    "runtime": {}
  }
}
```

输出：

```json
{
  "status": "success",
  "split_positions": [],
  "confidence": 0.8,
  "error": null
}
```

节点编排：

```text
Start
-> Code 输入提取
-> If/Else 空消息判断
-> Template Transform 首次 Prompt
-> LLM 首次切分
-> Code JSON 校验
-> If/Else 有效？
   -> End
   -> Template Transform 修复 Prompt 1
      -> LLM 修复 1
      -> Code 校验 1
      -> If/Else 有效？
         -> End
         -> Template Transform 修复 Prompt 2
            -> LLM 修复 2
            -> Code 校验 2
            -> Code 标准化最终输出
            -> End
```

Dify 内部重试：

```text
首次输出 + 2 次修复 = 最多 3 次 LLM 尝试
```

系统侧重试：

```text
如果 Dify 返回 failed 或系统校验失败，自建系统最多重新发起 1 次 Dify run。
```

彻底失败：

```text
conversation_boundary_job=failed
记录 chatid/date/run_id/error/last_invalid_output
不写 conversation_segments
```

## 3. 阶段二：会话入库与画像更新请求创建

### 3.1 会话入库

系统收到 `split_positions` 后：

```text
校验切分点
-> 按消息顺序生成会话段
-> 写入 conversation_segments
-> 提取 participants
```

第一版可以先把 `title/summary/keywords` 设为系统占位值，等后续需要再增加会话摘要生成工作流。

### 3.2 画像更新请求创建

每个会话入库后：

```text
for userid in participants:
  create profile_update_request(conversation_no, userid, source_profile_version)
```

注意：

- 机器人 userid 不创建画像更新请求。
- 缺失 userid 的消息不能创建画像更新请求。
- 一个会话内多个用户可以创建多个请求。

## 4. 阶段三：画像更新工作流

### 4.1 目标

一次更新一个用户画像：

```text
一个 conversation 的全部消息
+ 一个 target_userid
+ 该用户当前画像
-> Dify 输出该用户的更新画像
```

### 4.2 并发策略

必须异步并行，但要保护状态：

```text
不同 userid 可并行
同一 userid 同时最多一个 running/writing 请求
```

原因：

- 画像输出依赖原画像。
- 如果同一用户多个请求并发拿到同一旧版本，会互相覆盖。
- 第一版用状态机和版本检查解决，不引入分布式锁。

### 4.3 状态机

建议新增：

```text
profile_update_requests
```

状态：

```text
pending
claimed
running
succeeded
writing
completed
no_change
failed
version_conflict
stalled
canceled
```

关键规则：

- claim 后立即提交事务。
- Dify blocking 前写 `running` 并提交事务。
- 写画像前重新读取当前 profile version。
- 当前 version 与 `source_profile_version` 不一致时，标记 `version_conflict`，不得覆盖写入。
- Dify 失败只影响当前 request，不阻塞其他用户。

### 4.4 Dify 工作流

工作流建议命名：

```text
user_profile_update
```

输入：

```json
{
  "payload": {
    "userid": "USER_A",
    "conversation": {
      "conversation_no": "conv_20260603_abc123",
      "chatid": "CHAT_A",
      "started_at": "2026-06-03T09:00:00+08:00",
      "ended_at": "2026-06-03T09:20:00+08:00"
    },
    "messages": [],
    "target_user_messages": [],
    "current_profile": {},
    "runtime": {}
  }
}
```

必须记住的契约：

- `conversation_no` 必须位于 `payload.conversation.conversation_no`。
- 不再支持旧的顶层 `payload.conversation_no` 作为正式输入。
- `target_user_messages` 必须只包含 `payload.userid` 对应用户自己的消息。
- `messages` 必须包含本会话全部消息，包括机器人回复和其他用户消息。
- 如果 `conversation.conversation_no` 缺失，Dify 会返回 `profile_action=no_change` 兜底，而不是进入画像更新 LLM。

输出：

```json
{
  "userid": "USER_A",
  "profile_action": "update",
  "updated_profile": {
    "summary": "",
    "facts": []
  },
  "changes": {
    "facts_added": [],
    "facts_updated": [],
    "facts_retired": []
  },
  "evidence": {
    "conversation_no": "",
    "msgids": []
  },
  "confidence": 0.8
}
```

Dify 内部同样采用：

```text
首次 LLM + 2 次修复 LLM
```

## 5. 阶段四：回复工作流画像化

画像可用后，需要重写现有两个回复类 Dify 工作流：

```text
group_knowledge_reply
chat_proactive_reminder
```

### 5.1 group_knowledge_reply

系统侧在调用 Dify 前读取提问用户画像：

```json
{
  "payload": {
    "question": "",
    "message": {},
    "recent_messages": [],
    "user_profile": {
      "userid": "USER_A",
      "summary": "",
      "facts": []
    },
    "runtime": {}
  }
}
```

目标：

- 回答仍以知识库和当前问题为主。
- 用户画像只用于个性化表达、补充背景和减少重复解释。
- 不允许暴露画像中敏感或不应展示的内部判断。
- 输出结构保持当前回复链路兼容，不改变发送系统字段。

### 5.2 chat_proactive_reminder

系统侧在主动回复判断时传入相关用户画像：

```json
{
  "payload": {
    "messages": [],
    "members": [],
    "user_profiles": [],
    "runtime": {}
  }
}
```

目标：

- 主动回复更贴合用户关注点。
- `target_userids` 仍必须来自输入。
- `quote_msgid` 仍必须来自输入。
- 输出结构保持不变：

```json
{
  "should_send": true,
  "target_userids": [],
  "quote_msgid": "",
  "content": "",
  "confidence": 0.8
}
```

## 6. 推荐实施顺序

### Step 1：文档与契约冻结

已完成或本阶段完成：

- 更新会话切分模块文档。
- 更新用户画像模块文档。
- 固定 Dify 内部重试和系统侧重试规则。
- 固定画像异步并行状态机规则。

### Step 2：会话切分后端状态

串行先做：

- 新增或明确 `conversation_boundary_jobs` 状态记录。
- 支持每天一次按 `chatid/date` 创建任务。
- 构造单日全量 `payload.messages`，包含机器人回复。
- 接收 `split_positions` 并切分入库。

### Step 3：会话切分 Dify DSL

可与 Step 2 部分并行，但必须共享输出 schema：

- 创建 `conversation_boundary_detection.dify.yml`。
- 使用中文节点标题和描述。
- 使用两次修复链路。
- Code 节点输出必须符合 Dify 1.14.2 类型限制。

### Step 4：画像更新状态机

会话切分入库后做：

- 新增 `profile_update_requests`。
- 实现 claim/running/completed/version_conflict。
- 支持不同用户并行，同用户串行。

### Step 5：画像更新 Dify DSL

可与 Step 4 部分并行：

- 创建 `user_profile_update.dify.yml`。
- 输入一个 conversation + target userid + current profile。
- 输出完整 `updated_profile + changes`。
- 使用两次修复链路。

### Step 6：回复工作流画像化

画像更新可用后做：

- 重写 `group_knowledge_reply` payload，增加 `user_profile`。
- 重写 `chat_proactive_reminder` payload，增加 `user_profiles`。
- 保持输出结构不变，避免破坏已稳定的发送链路。

### Step 7：回归与发布

串行收口：

- 单日消息能生成切分点。
- 切分点能正确写会话段。
- 一个会话能为多个用户创建画像更新请求。
- 不同用户画像更新可并行。
- 同用户画像不会并发覆盖。
- @ 回复和主动回复能读取画像并传给 Dify。

## 7. 暂不进入本阶段

- Dify streaming。
- Redis 队列和分布式锁。
- 复杂人工审核流。
- 复杂会话摘要二次生成。
- 大屏统计。
