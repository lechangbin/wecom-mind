# 基于自建系统 + Dify 的企微智能机器人架构文档

## 1. 文档目标

本文档描述一个基于企业微信智能机器人、企微 MCP 能力、自建业务系统和 Dify 的群聊 AI 机器人系统架构。当前阶段以前后端功能实现为主，前端数据看板仅预留接口和统计字段，不作为核心建设重点。

本架构用于指导后续需求拆分、数据库设计、接口设计和开发实现。

## 2. 核心结论

本项目采用“自建系统主控 + Dify AI 子工作流”的混合架构。

- 自建系统负责确定性业务逻辑：企微回调接收、群消息拉取、消息入库、排重、任务调度、Dify 调用、结果校验、核心表写入、企微消息发送和审计。
- Dify 负责不确定性 AI 逻辑：意图识别与动作决策、通用回复生成、会话切分、会话摘要、用户画像生成与更新。
- Dify 输出仅作为结构化建议结果，自建系统拥有最终写库权和发送权。
- MVP 阶段不建设 Internal MCP Server。Dify 如需读取数据，优先由自建系统组装上下文 JSON 传入；必要时开放受控 REST API 给 Dify 查询。
- 前端后台作为管理和统计展示模块预留，当前不作为架构重点。

## 3. 系统边界

### 3.1 系统内职责

自建系统负责：

- 接收企微 MCP/webhook 回调。
- 根据回调直接入库，或按游标/事件拉取群消息。
- 保存群聊、用户、消息、机器人回复、Dify 调用、会话摘要、用户画像和发送任务。
- 识别 @ 事件触发、关键词定时扫描、定时意图等触发场景。
- @ 触发判断留在自建系统，Dify 的 `reply_generation` 只负责生成回复内容。
- 调用不同 Dify 工作流，并校验 Dify 返回 JSON。
- 将合法 AI 结果写入数据库。
- 通过企业微信能力发送普通消息、主动 @ 消息、流式回复或模板卡片。
- 提供管理后台和课程展示所需的数据接口。

Dify 负责：

- 根据自建系统提供的 JSON 输入完成 AI 推理。
- 返回稳定 schema 的 JSON 输出。
- 支持后续新增或替换 AI 工作流。

企业微信负责：

- 群聊消息产生与回调通知。
- 智能机器人长连接或 webhook 相关消息能力。
- 群消息拉取能力。
- 消息发送、@ 用户、流式回复、模板卡片等交互能力。

### 3.2 暂不纳入 MVP 的内容

- Internal MCP Server。
- 多租户 SaaS 化。
- 复杂权限体系。
- 完整前端可视化大屏。
- 全量历史聊天记录迁移。
- 复杂运营配置中心。

## 4. 总体架构

系统由以下核心层组成：

1. 企微接入层
   - 企微 MCP/webhook 回调接收。
   - 群消息拉取。
   - 智能机器人回复通道。
   - 普通 webhook 备用通知通道。

2. 消息处理层
   - 原始消息保存。
   - 标准化消息转换。
   - 幂等排重。
   - 附件元数据保存。
   - 消息上下文窗口构建。

3. 触发与任务层
   - @ 事件触发。
   - 关键词定时扫描线索。
   - 定时意图扫描。
   - 会话切分定时任务。
   - 用户画像分析定时任务。

4. Dify 调用层
   - 工作流注册。
   - 输入 JSON 构造。
   - blocking/streaming 调用。
   - 输出 JSON 校验。
   - 调用日志和失败记录。

5. AI 结果处理层
   - 回复结果处理。
   - 会话切分结果处理。
   - 用户画像结果处理。
   - 主动推送建议处理。

6. 发送层
   - 流式回复。
   - 普通回复。
   - 主动群消息。
   - @ 指定用户消息。
   - 模板卡片。
   - 发送失败重试。

7. 管理与统计层
   - 消息查询。
   - 会话摘要查看。
   - 用户画像查看。
   - Dify 运行日志。
   - 基础统计看板。

## 5. 推荐运行链路

### 5.1 群消息采集链路

1. 企业微信产生群消息。
2. 企微 MCP/webhook 通知自建系统。
3. 自建系统校验回调来源和签名。
4. 如果回调带完整消息，直接写入原始消息表。
5. 如果回调只带事件或游标，自建系统创建拉取任务。
6. 拉取 Worker 获取群消息。
7. 消息进入标准化流程。
8. 写入消息表。
9. 触发规则引擎按链路评估：@ 事件由自建系统直接触发 `reply_generation`，关键词由后续定时扫描窗口作为 `intent_detection` 输入线索。

### 5.2 @ 实时回复链路

1. 用户在群内 @ 机器人。
2. 企微通过 @ 事件回调或长连接实时消息通知自建系统。
3. 触发器识别为 `mention`。
4. 自建系统读取上下文、用户画像、历史摘要。
5. 自建系统调用 Dify 的 `reply_generation` 工作流。
6. 若后续启用流式回复，自建系统将 `reply_generation` streaming 输出转发到企微流式回复接口。
7. 最终回复结果写入 `bot_replies` 和 `outbox_messages`。

### 5.3 关键词与定时意图识别链路

1. 消息先通过当前企微接入通道完成入库。
2. 调度器按群和时间窗口扫描新消息。
3. 自建系统按关键词规则匹配消息内容。
4. 自建系统把消息窗口、命中关键词和已知用户传给 `intent_detection`。
5. Dify 返回动作建议、目标用户、证据消息和回复指令。
6. 自建系统校验动作结果。
7. 如需回复，自建系统调用 `reply_generation` 生成最终消息正文。
8. Outbound Dispatcher 创建并发送消息。

### 5.4 会话切分链路

1. 调度器按群或时间窗口扫描未切分消息。
2. 自建系统先按时间间隔、消息数量和已知边界生成候选窗口。
3. 调用 Dify 会话切分工作流。
4. Dify 返回会话边界、标题、摘要、关键词、参与人。
5. 自建系统校验消息边界是否存在且合法。
6. 写入会话切分表和摘要表。

### 5.5 用户画像链路

1. 调度器按用户活跃度或消息增量选择待分析用户。
2. 自建系统组装用户个人消息、参与会话摘要、近期行为统计。
3. 调用 Dify 用户画像生成与更新工作流。
4. Dify 返回画像新增、更新或退役建议。
5. 自建系统校验证据消息、置信度和字段类型。
6. 写入画像事实表，并更新用户画像快照。

## 6. 关键架构原则

1. 自建系统是状态中心。
2. Dify 是 AI 推理中心，不是核心数据库写入者。
3. 企微回调必须快速响应，耗时任务异步处理。
4. 所有消息、任务和发送行为必须可追踪。
5. 所有外部回调和 AI 输出必须校验。
6. 所有核心写入必须具备幂等键。
7. Dify 工作流以 `workflow_code + version + input_schema + output_schema` 管理。
8. 前端展示需求反向影响统计字段，但不主导当前架构。

## 7. 重点待确认事项

1. 企微 MCP webhook 回调是否直接携带完整消息，还是只携带事件/游标。
2. 企微侧流式回复在当前账号能力下是否可用。
3. 企微回复是否能稳定表现为“引用原消息回复”，需要真实环境验证。
4. Dify 部署形态：云端 Dify 还是自部署 Dify。
5. Dify 是否允许直接只读访问数据库；若允许，需要限制账号权限。
