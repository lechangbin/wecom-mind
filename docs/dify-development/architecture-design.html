Architecture Baseline

自建系统主控，Dify 作为 AI 子工作流引擎

本架构把 Dify 调用统一收敛到 API blocking。自建系统构造业务 payload、保存 ai_runs、校验 outputs、写库和发送；Dify 只处理语义判断、回复生成、会话切分和画像演进。

/v1/workflows/run Start: payload LLM + Code Blocking 验收
1 Start 节点变量：只保留 payload，类型为 json_object。
4 Dify 工作流：意图识别、回复生成、会话切分、用户画像。
0 Dify 不写库、不发企微、不承担幂等和重试。

Dify 内部节点编排

Start

接收 payload: json_object，不拆数组字段。

Code normalize

提取字段、归一化数组、生成 LLM 输入和 fallback。

LLM

完成语义判断、生成、摘要或画像推理，只输出 JSON。

Code finalize

解析 JSON、校验证据和用户、兜底异常输出。

End

只声明正式业务字段，直接作为 data.outputs。

工作流矩阵

workflow_code 职责 输入重点 End outputs 关键红线
intent_detection 判断消息窗口是否需要回复、建任务或忽略。 消息窗口、命中关键词、已知用户、已有动作。 actions 不能输出最终回复正文。
reply_generation 生成唯一可发送的企业微信回复正文。 回复场景、回复指令、证据消息、上下文、画像。 action、reply、metadata、confidence 回复必须基于输入证据，可直接发送。
conversation_segmentation 输出主题会话切分建议。 chatid、window、messages、候选边界。 segments 起止 msgid 和参与人必须来自输入。
user_profile_analysis 输出用户画像新增、更新、退役或不变建议。 userid、近期消息、会话摘要、当前画像、统计特征。 userid、profile_action、facts_to_add 等 不能编造 fact_id、msgid 或敏感事实。

运行链路

@ 回复链路

企微消息入库后，自建系统识别显式 @，构造 reply_generation payload，调用 Dify blocking，校验回复输出，再创建 outbox。

mentioned_bot reply_generation outbox

关键词与定时意图

调度器扫描消息窗口，关键词只是召回线索。Dify 输出 actions；如果需要回复，自建系统再调用 reply_generation。

keyword_scan intent_detection reply_generation

会话切分

自建系统选择消息窗口，Dify 输出 segments。自建系统校验边界、参与人和重叠区间，再生成 conversation_no 并写库。

messages segments conversation_no

用户画像

自建系统提供用户近期消息、会话摘要和当前画像。Dify 输出画像演进建议，自建系统校验证据后生成新版本。

recent_messages facts profile_version

风险控制

  • Dify API 响应不是 data.status=succeeded 时，自建系统必须记录失败，不消费 outputs。
  • outputs 缺字段、字段类型不匹配、引用不存在的 msgid 或 userid 时，必须进入 invalid_output。
  • Webhook ack 不是业务 outputs，在没有结果回收机制前不能作为主链路。
  • LLM 输出 JSON 外说明文字时，finalize Code 必须解析或兜底，不能让散文进入 End。
